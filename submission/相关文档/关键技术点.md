# LabelHub 关键技术点

本文档面向比赛评审和后续技术交接，说明 LabelHub 数据标注平台中最能体现系统设计、工程复杂度和业务价值的关键技术点。文档重点不是重复提交包 README，而是说明每个技术点解决了什么问题、采用了什么方案、在哪些模块落地，以及如何验收。

当前系统已经部署到生产环境，线上入口为 `https://www.scu-gpt.top/labelhub/`。本文不包含生产密码、数据库口令、Redis 口令、Turnstile secret key 或 LLM API Key。

## 1. 技术主线

LabelHub 的核心技术主线是“多人协作标注 + AI 预审 + 人工复核 + 可追溯交付”。系统不是单页表单工具，而是围绕标注项目完整生命周期设计：

1. Owner 准备数据、模板和任务。
2. Labeler 领取任务并提交结构化答案。
3. 后端基于提交结果创建 AI 预审作业。
4. 独立 Agent 异步调用 LLM 并回写结构化结果。
5. Reviewer 结合 AI 结果完成人工裁决。
6. Owner 通过看板、审计和导出完成项目交付。

这一主线决定了系统需要处理以下工程问题：

- 多角色权限与工作台隔离。
- 动态 Schema 表单的设计、渲染、校验和版本一致性。
- 标注、审核、AI Job、导出等实体的状态流转约束。
- 异步 AI 任务领取、并发执行、失败回写和幂等保护。
- 模型 API Key 的生产安全保存和运行时下发。
- 生产子路径部署、静态资源 base path、API 反向代理和数据库迁移。

## 2. 多角色协作闭环与权限隔离

### 解决的问题

数据标注项目通常涉及任务负责人、标注员、审核员和系统 Agent。如果所有角色共用一套页面和接口权限，容易出现误操作、流程绕过和数据边界不清的问题。

### 技术方案

系统把用户角色拆成 Owner、Labeler、Reviewer、AI Reviewer 和 `system_agent`：

- 前端通过不同路由和工作台布局呈现不同职责。
- 后端通过 token 会话、角色列表和接口层校验限制访问。
- `system_agent` 只用于机器登录和 AI 作业处理，不作为普通 Web 用户使用。
- Owner 可通过邀请机制创建 Reviewer 或 Owner 邀请，避免生产环境沿用默认演示账号。

### 关键实现依据

- `AuthService` 中对登录角色做白名单校验，普通用户登录需要 Turnstile，人机验证只允许 `system_agent` 在服务令牌匹配时绕过。
- `TokenService` 与 Redis 会话结合，支撑登录态刷新、退出和当前用户识别。
- 前端 `AppLayout` 按角色组织导航，Owner、Labeler、Reviewer 和 AI Reviewer 的页面入口互相隔离。
- `AuthService` 中 Reviewer/Owner 邀请码使用强随机 token，并在数据库侧保存 hash，降低邀请码泄露后的风险。

### 业务价值与验收方式

业务价值：

- 角色职责清晰，评审时可以按真实业务流程切换账号验证。
- 生产环境不依赖演示账号，符合基本安全要求。
- Agent 与人工用户隔离，避免机器账号被误用于页面操作。

验收方式：

1. 使用 Owner 登录，只能进入 Owner 相关管理页面。
2. 使用 Labeler 登录，只能领取任务、标注和处理返修。
3. 使用 Reviewer 登录，只能进入审核工作台和争议样本。
4. 关闭或禁用演示账号后，登录页不再展示演示账号入口。

## 3. 动态 Schema 模板设计、渲染与校验

### 解决的问题

不同标注任务的数据结构差异很大：有的只需要文本分类，有的需要多字段评分、JSON、附件上传、多 Tab 布局或 LLM 辅助字段。如果每类任务都写独立页面，系统无法快速扩展。

### 技术方案

LabelHub 使用动态 Schema 描述标注表单：

- Owner 在模板设计器中拖拽物料，配置字段名、标签、选项、校验规则、联动规则和布局。
- 前端运行时把 Schema 编译为 Formily schema，并渲染为实际标注表单。
- 后端保存 Schema 版本，发布后作为标注和审核的稳定快照。
- 后端校验 Schema 结构，防止重复字段名、非法物料、非法正则和错误联动引用。
- 前后端均支持 `group` 和 `multi-tab` 等嵌套字段结构，避免布局字段导致答案丢失。

### 关键实现依据

- 前端 `OwnerTemplateDesigner` 提供模板设计入口，支持基础字段、布局字段、展示字段和 LLM 触发组件。
- 前端 `schemaCompiler` 将 Schema 字段转换为 Formily schema，并处理 required、visible、hidden、visibleRequired 等运行时联动。
- 前端 `LabelHubFormRenderer` 复用同一套渲染器服务模板预览和 Labeler 答题页，减少设计态与运行态不一致。
- 前端 `schemaTree` 负责展开和规范化 `group`、`multi-tab` 中的嵌套字段。
- 后端 `SchemaDefinitionValidator` 对字段类型、字段名、选项、校验器、正则和联动规则做服务端校验。
- 后端 `SchemaFieldTree` 统一展开嵌套字段，供答案过滤、附件校验、导出和 LLM 触发复用。

### 业务价值与验收方式

业务价值：

- Owner 不需要开发新页面即可配置不同标注任务。
- 同一个 Schema 同时用于答题、审核展示、导出字段选择和 LLM Prompt 上下文。
- 服务端校验避免前端绕过后写入非法模板。

验收方式：

1. 创建包含单选、多选、文本、JSON、附件和多 Tab 的模板。
2. 发布模板并创建任务。
3. Labeler 答题页应按模板结构渲染。
4. 配置联动规则后，目标字段应按条件显示、隐藏或变为必填。
5. 尝试提交不合法 JSON 或缺失必填字段，应在前端或后端被拦截。

## 4. 数据集导入、任务范围与题量分配

### 解决的问题

标注项目不仅需要上传数据，还需要控制每个任务包含哪些样本、哪些人能领取、每个人能处理多少题。如果只做简单文件上传，无法支撑真实项目管理。

### 技术方案

系统把数据集、任务和作业分离：

- 数据集模块负责创建数据集、导入样本和提供样本预览。
- 任务模块负责绑定数据集、模板、奖励、截止时间、AI 规则和题目范围。
- Owner 可以配置 Labeler 和 Reviewer 的参与范围与题量。
- Labeler 领取任务后生成真实 assignment，后续草稿、提交、附件和审核均围绕 assignment 流转。
- 任务市场和我的任务通过后端接口计算可领取、已领取、已完成和剩余额度。

### 关键实现依据

- `DatasetController` 提供数据集创建、导入、追加导入、分页查看和 item options。
- `TaskController` 提供任务创建、编辑、发布/暂停/结束、任务市场和领取接口。
- `TaskService` 与任务分配相关逻辑控制任务状态、领取条件、题量限制和人员范围。
- 接口文档中将任务创建字段拆成数据集、Schema、分配策略、AI 预审和 LLM 辅助开关，体现任务配置的组合能力。

### 业务价值与验收方式

业务价值：

- 数据可以复用，任务可以按范围拆分。
- 题量分配支持多人协作，不需要人工线下分发样本。
- 后续看板和导出可以基于任务维度聚合。

验收方式：

1. Owner 导入一个数据集。
2. 创建任务时选择数据集和题目范围。
3. 配置标注员和审核员题量。
4. Labeler 进入任务市场，只能领取符合条件的任务。
5. 题量达到上限后不应继续领取。

## 5. 标注答案一致性、草稿、提交与返修链路

### 解决的问题

标注过程需要支持草稿、正式提交、审核打回和重新提交。更复杂的是，Schema 可能在任务运行前后发生变化，如果不校验版本和字段，容易出现“用旧表单提交到新任务”的数据错位。

### 技术方案

系统围绕 assignment 管理 Labeler 作业：

- 答题页加载题目原始数据、Schema 快照、草稿、历史记录和当前位置。
- 草稿保存可保留当前答案，正式提交时进入审核链路。
- 请求中携带 `schemaDigest`，后端校验当前提交使用的 Schema 是否与服务端一致。
- 后端提交时过滤不可提交字段，避免展示字段、布局字段或隐藏字段污染答案。
- Reviewer 打回后，Labeler 可以在返修入口重新提交。
- 附件上传与 assignment 和 fieldName 绑定，后端校验对应字段是否为 file-upload 类型。

### 关键实现依据

- 前端 `AnswerPage` 按 assignment 加载题目、草稿和 Schema，并在保存草稿、提交答案时携带 `schemaDigest`。
- 后端 `AnnotationService` 解析 Schema 快照，校验 `schemaDigest`，并在提交后触发 AI 预审或人工审核。
- 后端 `AnswerValidationService` 根据 Schema 对必填、条件必填、字段类型和可见字段做服务端校验。
- 后端 `AssignmentAttachmentService` 使用 `SchemaFieldTree` 校验附件只能上传到文件字段。
- Labeler 草稿箱、返修项和问题上报接口共同覆盖标注过程中的中断、返工和异常反馈。

### 业务价值与验收方式

业务价值：

- 标注员可以中途保存，不必一次完成所有题目。
- Schema 变化不会悄悄破坏已提交数据。
- 返修链路闭环，不需要线下通知标注员。
- 附件与字段绑定，避免任意文件污染答案结构。

验收方式：

1. Labeler 保存草稿后刷新页面，应能继续编辑。
2. 提交缺失必填字段的答案，应返回校验错误。
3. Reviewer 打回后，Labeler 应能在打回项中看到并重新提交。
4. 对非附件字段上传文件，应被后端拒绝。

## 6. 状态机与审计日志

### 解决的问题

任务、标注、AI Job 和导出都有生命周期。如果状态流转只靠各业务代码随意修改，容易出现非法跳转，例如未提交直接审核通过、已成功导出又回到运行中、AI Job 被过期结果覆盖。

### 技术方案

系统抽象统一状态机服务：

- 为任务、assignment、annotation、AI Review Job 和 Export Job 定义允许状态。
- 对每个实体定义合法状态跳转。
- 状态变更时校验当前角色是否有权限执行该跳转。
- 每次关键动作写入审计日志，保存 entity、operator、action、fromState、toState、reason、before、after 和 snapshot。
- Owner 审核管理和 Reviewer 时间线可基于审计日志追溯题目流转过程。

### 关键实现依据

- `StateMachineService` 定义了 `TASK`、`ASSIGNMENT`、`ANNOTATION`、`AI_REVIEW_JOB`、`EXPORT_JOB` 的状态集合和跳转矩阵。
- `StateMachineService.audit()` 在写日志前校验状态跳转和角色权限。
- `WorkflowEntityType` 用统一枚举区分不同业务实体。
- `OwnerReviewController` 提供审核日志、题目时间线和任务审核跟踪接口。
- `AnnotationService`、`AiReviewService`、`ExportService` 等核心业务在状态变化时写入审计。

### 业务价值与验收方式

业务价值：

- 状态变化可追溯，方便 Owner 定位问题。
- 避免非法流程绕过，保证业务闭环可信。
- AI 预审、人工审核和导出都能沉淀为同一条时间线。

验收方式：

1. Labeler 提交后，题目状态应进入 AI 预审或人工审核。
2. Agent 完成预审后，状态应进入待人工审核或接受状态。
3. Reviewer 裁决后，Owner 审核页面应能看到操作记录。
4. 导出成功后，导出任务状态应变为 succeeded，并有导出审计记录。

## 7. AI 预审 Agent 异步执行链路

### 解决的问题

AI 预审调用 LLM 可能耗时较长、失败率受外部服务影响，不能阻塞用户提交接口，也不能让多个 Worker 重复处理同一条 Job。

### 技术方案

系统把 AI 预审拆成后端 Job 队列和独立 Agent：

- Labeler 提交答案后，后端根据任务和规则创建 AI Review Job。
- Agent 使用 `system_agent` 登录后端，通过 claim 接口领取下一条可执行 Job。
- 领取时后端返回 runToken，Agent 回写 complete/fail 时必须携带 runToken，避免过期执行结果覆盖新运行。
- Agent 根据后端 active 模型配置决定并发数、模型地址、模型名称和 API Key，缺失时使用环境变量兜底。
- Agent 使用 OpenAI-compatible Responses API，并要求模型输出符合严格 JSON Schema。
- 解析失败、LLM 调用失败或回写失败会进入 fail 流程，可由 Web 端重试。

### 关键实现依据

- `AiReviewWorker` 负责启动固定线程池、按并发轮询、领取 Job、调用 LLM、回写成功或失败。
- `BackendClient` 封装 Agent 到后端的登录、claim、complete、fail 和 runtime config 请求。
- `ResponsesLlmClient` 构造 Responses API 请求，并使用 `text.format.json_schema` 约束模型输出。
- `AiReviewOutputParser` 从 Responses 响应中解析 `output_text` 或嵌套 text，并转换为 `scores`、`totalScore`、`decision`、`comment`、`riskFlags` 和 `evidence`。
- `AiReviewService` 在后端负责 Job 领取、runToken 校验、状态变更、结果写入和失败处理。

### 业务价值与验收方式

业务价值：

- 用户提交不会被 LLM 调用阻塞。
- AI 预审可以横向扩展并发，适配不同部署资源。
- runToken 避免重复执行和过期结果覆盖。
- AI 输出结构化后可被 Reviewer 工作台、看板和导出复用。

验收方式：

1. Labeler 提交答案后，AI 队列应出现 pending Job。
2. Agent 运行后应 claim Job 并进入 running。
3. LLM 成功返回后，Job 应变为 succeeded，并生成 AI 结果。
4. 人为配置错误 API Key 时，Job 应失败并保留失败摘要。
5. 重试失败 Job 后，应生成新的运行过程，不应被旧 runToken 覆盖。

## 8. 模型配置安全与运行时配置下发

### 解决的问题

AI 能力需要配置模型供应商、base URL、模型名称和 API Key。生产环境不能把 API Key 写死在代码或前端静态资源中，也不能让 Agent 只能靠重启环境变量调整模型。

### 技术方案

系统提供 Web 端模型配置和 Agent 运行时拉取机制：

- Owner 或 AI Reviewer 可在模型配置页面维护多个模型配置。
- 后端保存 API Key 时使用服务端密钥加密。
- Agent 每次执行前优先读取后端 active runtime config。
- 当后端没有 active 配置时，Agent 才使用 `LABELHUB_LLM_*` 环境变量兜底。
- active 配置支持并发数下发，Agent 在启动时按后端配置调整 worker 数量。

### 关键实现依据

- `AiModelConfigCrypto` 使用 AES/GCM/NoPadding 加密模型 API Key，IV 随机生成，密钥来自 `LABELHUB_MODEL_CONFIG_SECRET` 的 SHA-256 摘要。
- `AiModelConfigService` 负责模型配置校验、保存、激活、删除保护和 runtime config 输出。
- `AiReviewWorker.resolveWorkerConcurrency()` 优先读取后端 runtime config 中的 workerConcurrency，再回退到本地环境变量。
- `ResponsesLlmClient.resolveRuntimeConfig()` 优先使用后端 active 配置，只有 404 或无配置时才回退环境变量。

### 业务价值与验收方式

业务价值：

- 模型配置可在线调整，不需要每次修改 Agent 镜像或容器环境变量。
- API Key 不进入前端，不以明文写入仓库。
- active 配置保护避免删除正在使用的模型配置。
- `LABELHUB_MODEL_CONFIG_SECRET` 保持稳定后，可长期解密历史保存的模型 Key。

验收方式：

1. Owner 创建模型配置并激活。
2. Agent 执行 AI 预审时使用 active 配置。
3. 删除 active 配置应被后端拒绝。
4. 未配置 `LABELHUB_MODEL_CONFIG_SECRET` 时保存或读取 API Key 应失败并提示需要配置密钥。

## 9. Labeler 侧 LLM 辅助与字段级触发

### 解决的问题

标注员在处理复杂样本时，常常需要理解原始数据、字段要求和候选判断。直接让标注员离开系统去问外部模型，会导致上下文丢失、答案格式不一致和安全风险。

### 技术方案

系统在 Labeler 答题页内提供 LLM 辅助：

- 通用 LLM 助手用于解释题目、Schema 字段和判断思路。
- 模板设计器支持 `llm-trigger` 字段，Owner 可以配置上下文字段、目标字段、任务说明和输出要求。
- Labeler 点击触发后，后端基于当前题目、Schema、已有答案和配置生成 Prompt。
- LLM 返回的建议不会自动强制覆盖答案，而是由 Labeler 确认后应用到目标字段。
- 字段级触发状态由渲染器维护，避免不同题目或不同 Schema 间状态串扰。

### 关键实现依据

- `OwnerTemplateDesigner` 支持 `llm-trigger` 物料和目标字段配置。
- `LabelHubFormRenderer` 管理 `llmTriggerStates`，并提供 `onApplyLlmResult`、`onApplyLlmResults` 给 LLM 触发组件。
- `AnnotationController` 暴露 `/labeler/assignments/{assignmentId}/assistant` 和 `/labeler/assignments/{assignmentId}/llm-trigger`。
- `LabelerAssistantService` 和 `LabelerLlmTriggerService` 组装 Prompt、调用模型配置并返回建议。
- 后端使用 `SchemaFieldTree` 查找目标字段和上下文字段，保证嵌套布局中的字段也能被识别。

### 业务价值与验收方式

业务价值：

- AI 不只参与审核，也能在标注阶段降低理解成本。
- Owner 可按模板控制 LLM 辅助的作用范围和输出目标。
- Labeler 保留最终选择权，避免模型建议直接污染答案。

验收方式：

1. 在模板中配置 LLM 触发组件和目标字段。
2. Labeler 答题时点击触发按钮。
3. 页面显示模型建议和可应用结果。
4. 点击应用后，目标字段值更新，但仍可人工修改。

## 10. Reviewer 三栏审核、争议样本与时间线

### 解决的问题

人工审核需要同时看原始样本、标注答案和 AI 建议。如果页面只展示一个结论，审核员无法判断 AI 和标注员的分歧来源，也无法给出可追溯裁决。

### 技术方案

Reviewer 工作台采用三栏审核思路：

- 左侧查看样本原始内容和任务上下文。
- 中间查看 Labeler 提交的结构化答案。
- 右侧查看 AI 建议、评分、风险标签和人工裁决入口。
- Reviewer 可执行通过、打回、争议和终审处理。
- 题目时间线展示 assignment、annotation、AI job 和 human review 的关键事件。

### 关键实现依据

- `ReviewController` 提供 Reviewer 概览、批次领取、AI 预审任务、任务下标注明细、人工裁决、争议样本和报表接口。
- `ReviewService` 负责聚合样本、答案、AI 结果、人工审核和争议信息。
- `OwnerReviewController` 提供 Owner 侧只读审核跟踪、审计日志和题目时间线。
- 前端 Reviewer 页面按任务聚合 AI 预审项，并在工作台中展示样本、答案和 AI 结果。

### 业务价值与验收方式

业务价值：

- 审核员不需要在多个页面之间反复切换。
- AI 结论成为人工裁决的辅助依据，而不是替代人工判断。
- 打回和争议都有记录，方便 Owner 追踪质量问题。

验收方式：

1. Reviewer 打开 AI 审核任务。
2. 进入某个任务的审核工作台。
3. 查看样本、Labeler 答案和 AI 建议是否同屏展示。
4. 执行通过、打回或争议裁决。
5. Owner 在审核管理中查看对应时间线和审计日志。

## 11. Owner 数据看板、导出中心与交付闭环

### 解决的问题

标注项目最终要交付可用数据，而不只是完成页面操作。Owner 需要知道任务进度、质量分布、审核负载、争议风险，并能导出稳定格式的结果。

### 技术方案

系统提供 Owner 看板和导出中心：

- Dashboard 聚合任务进度、审核分布、角色人数、提交趋势、标注员表现、争议和到期风险。
- 导出中心只导出已验收或可导出的标注结果，避免未审核数据混入交付物。
- 导出支持 JSON、JSONL、CSV 和 XLSX。
- 导出字段可以来自系统字段、题目原始数据和答案字段。
- 导出任务有状态、进度、文件元数据、下载地址和下载确认。
- 导出文件保存到后端持久化目录，并记录 SHA-256 校验信息。

### 关键实现依据

- `DashboardController` 和 `DashboardService` 提供 Owner 看板、报表和问题反馈数据。
- `ExportService` 支持创建导出任务、生成多格式文件、保存文件元数据、下载和下载确认。
- `ExportService` 使用 `SchemaFieldTree` 展开答案字段，自动生成可导出字段选项。
- 导出任务使用 `StateMachineService` 写入开始、成功、失败和纳入导出的审计记录。
- `ExportService` 对下载路径做 normalize 和 root 前缀校验，避免路径穿越。

### 业务价值与验收方式

业务价值：

- Owner 可以从项目运营视角查看质量和进度。
- 导出结果带有任务、题目、标注员、审核员、AI 结果和人工结果等上下文。
- 多格式导出适配后续数据处理、人工检查和归档。

验收方式：

1. 完成至少一条通过审核的标注。
2. Owner 打开看板，查看任务进度和审核分布。
3. 在导出中心创建 CSV 或 XLSX 导出。
4. 下载文件并检查字段是否包含系统字段和答案字段。
5. 下载确认后，导出记录应更新 downloadedAt。

## 12. 生产部署、子路径适配与数据库迁移

### 解决的问题

比赛部署场景通常不是根域名独占，而是挂在已有站点的子路径下。前端静态资源、路由、API 代理、Turnstile site key、Nginx 和 Docker Compose 都需要统一适配，否则会出现刷新 404、接口路径错误或静态资源加载失败。

### 技术方案

系统采用 Docker Compose + 宿主机 Nginx 的生产部署方式：

- 前端构建时设置 `VITE_APP_BASE_PATH=/labelhub/` 和 `VITE_API_BASE_URL=/labelhub/api`。
- 前端容器内 Nginx 提供静态资源和 SPA 路由回退。
- 宿主机 Nginx 将 `/labelhub/` 转发到前端容器，将 `/labelhub/api/` 转发到后端 `/api/`。
- 后端、前端只绑定宿主机回环地址，MySQL 和 Redis 仅在 Docker 网络内访问。
- `db-migrate` 使用官方 `mysql:8.0` 客户端镜像执行迁移，并用 `schema_migrations` 记录已执行版本。
- 生产 `.env` 管理数据库、Redis、Turnstile、服务令牌、模型配置和镜像标签。

### 关键实现依据

- `frontend/Dockerfile` 通过构建参数注入 base path、API base URL、Turnstile site key 和演示视频地址。
- `infra/nginx.conf` 定义 `/labelhub/` 和 `/labelhub/api/` 的反向代理规则。
- `infra/docker-compose.yml` 定义 MySQL、Redis、backend、agent、frontend 和 db-migrate。
- `docs/deployment-labelhub.md` 记录镜像构建、服务器准备、首次初始化、迁移执行和 Nginx 接入流程。
- `db-migrate` 按版本号执行 `V*.sql`，并在 demo 用户关闭时禁用本地演示账号。

### 业务价值与验收方式

业务价值：

- 系统可稳定部署在既有 HTTPS 域名的子路径下。
- 数据库迁移可重复执行，不会反复应用旧 SQL。
- 服务端口暴露最小化，符合生产安全边界。

验收方式：

1. 打开 `https://www.scu-gpt.top/labelhub/`，确认首页加载正常。
2. 刷新 `/labelhub/login` 和 `/labelhub/owner/tasks` 等深层路由，不应 404。
3. 前端请求应命中 `/labelhub/api`。
4. 执行 `docker compose --env-file .env --profile migrate run --rm db-migrate`，已执行迁移应显示跳过。
5. MySQL 和 Redis 不应对公网开放。

## 13. 安全边界与生产约束

### 已落实的安全设计

- 登录和注册接入 Cloudflare Turnstile，降低自动化撞库和垃圾注册风险。
- `system_agent` 绕过 Turnstile 必须同时满足角色为 `system_agent` 和服务令牌匹配。
- Redis token 会话支持退出和当前用户解析。
- 模型 API Key 使用 AES-GCM 加密保存，不进入前端静态资源。
- Reviewer/Owner 邀请码使用强随机明文 token 发给用户，数据库保存 hash。
- 导出下载路径做根目录约束，避免路径穿越。
- 生产部署不开放 MySQL 和 Redis 公网端口。
- 生产提交文档不写入真实密钥和口令。

### 当前边界

- 当前生产规格更适合比赛演示和小规模试用，长期运行建议升级服务器资源。
- 单次数据集导入和附件上传仍受后端与 Nginx 上传大小限制约束。
- AI 预审结果受模型质量、Prompt、规则配置和样本内容影响，Reviewer 仍是最终裁决者。
- `LABELHUB_MODEL_CONFIG_SECRET` 首次保存模型配置后必须保持稳定，随意更换会导致历史模型 Key 无法解密。
- `infra/.env` 是生产核心配置，需要单独备份和权限控制。

## 14. 后续增强方向

结合当前实现，后续可以按以下方向增强：

1. 引入对象存储，支撑更大规模附件和导出文件。
2. 增加集中日志、服务指标和告警，覆盖 Agent 失败率、LLM 延迟、导出失败率和数据库容量。
3. 为状态机和关键流程补充更完整的集成测试。
4. 将 `docs/state-machine.md`、`docs/architecture.md` 和 `docs/api-docs.md` 补齐为独立技术文档。
5. 增加数据备份和恢复演练脚本，降低生产数据风险。
6. 根据真实项目反馈细化权限模型，例如项目级 Owner、任务级 Reviewer 和导出权限审批。

## 15. 总结

LabelHub 的关键技术价值集中在三点：

1. 用动态 Schema 和统一渲染/校验机制支撑不同类型标注任务。
2. 用状态机、审计日志、AI Agent 和人工审核工作台把“标注-预审-复核-导出”做成可追溯闭环。
3. 用生产部署、安全配置和模型配置管理把演示系统推进到可上线验证的工程形态。

这些技术点共同支撑了当前生产环境中的完整业务流程，也为后续扩大数据规模、提升审核质量和接入更多模型供应商留下了清晰扩展空间。
