# 问题点归档

> 说明：本文档按增量方式记录实施中遇到的问题、原因、处理方式和后续建议。

## 01 MySQL 初始化脚本路径执行问题

### 现象

首次通过 `mysql -e "source ..."` 执行 `backend/src/main/resources/db/migration/V1__init_labelhub_schema.sql` 时，MySQL 客户端提示无法打开脚本文件。

### 原因

Windows 路径包含中文目录，`mysql source` 在 `-e` 参数中解析该路径不稳定，导致文件打开失败。

### 处理

改用标准输入方式执行 SQL 文件：`mysql ... < backend/src/main/resources/db/migration/V1__init_labelhub_schema.sql`。该方式已成功完成 `labelhub` 建库建表。

### 后续建议

后续自动化脚本优先使用标准输入或后端迁移工具执行 SQL，避免在 MySQL `source` 命令中直接传递包含中文字符的绝对路径。

## 02 数据集导入未做真实 MySQL 写入联调

### 现象

本次已完成数据集后端接口、文件解析、前端上传/新建弹窗和构建验证,但未直接向本地 `labelhub` MySQL 执行新建/导入写入联调。

### 原因

数据集导入会写入 `files`、`datasets`、`items` 多张表,属于数据库写操作。为避免在未确认当前本地库数据状态时写入额外测试记录,本次只执行后端与前端构建验证。

### 处理

已通过 `backend/.\mvnw.cmd -q -DskipTests package` 和 `frontend/npm run build` 验证编译、类型和打包链路。接口实现保持事务边界,写入失败会整体回滚。

### 后续建议

在确认可写测试库或准备好可清理的测试数据后,用 Owner 账号登录并依次验证 `POST /api/datasets`、`POST /api/datasets/import`、`GET /api/datasets`、`GET /api/datasets/{id}/items` 的真实数据库闭环。

## 03 指派分发策略缺少指派名单模型

### 现象

任务创建表单已经支持 `assigned` 分发策略,任务市场也能按策略展示和筛选,但当前数据库只有 `assignments` 结果表,没有 Owner 配置“哪些标注员可被指派”的名单表或接口。

### 原因

现有 `assignments` 表可以表达“某个 item 已经分配给某个 labeler”,但不适合承载待分配名单、批量指派规则和 Owner 端配置。若在 `POST /api/tasks/{taskId}/claim` 中允许任意标注员领取 `assigned` 任务,会破坏指派语义。

### 处理

本次后端实现采取保守策略:如果当前标注员已经有该任务的预分配 assignment,接口返回该记录;否则 `assigned` 任务拒绝自助认领并返回 `ASSIGNED_TASK_NOT_CLAIMABLE`。

### 后续建议

后续需要补 `task_assignees` 或等价配置模型,并在 Owner 端提供指派标注员入口;发布或指派时预生成 `assignments`,Labeler 端只展示/领取属于自己的指派任务。

## 问题:单角色演示账号无法在顶栏切换到其它角色

- 现象:使用 `owner`、`labeler`、`reviewer` 这类单角色演示账号登录后,顶栏“切换角色”只显示当前账号已有角色,因此看起来无法切换到其它工作台。
- 原因:顶栏角色切换基于当前登录用户的 `roles` 列表,不是重新登录其它演示账号;原有三个演示账号在后端分别只绑定一个角色。
- 处理:保留顶栏“当前账号内切换角色”的语义,新增 `demo / demo123` 多角色演示账号,同时绑定 `owner`、`labeler`、`reviewer`。

- 现象:在 Windows PowerShell 中执行 `npm run build` 时,系统提示禁止加载 `npm.ps1`。

- 后续建议:本地验证前端时优先使用 `npm.cmd ...`,或在确认安全策略允许的情况下调整 PowerShell 执行策略。

## 问题:Labeler 答题页只显示第 1 / 1 题

- 现象:Owner 发布任务时关联了整个数据集,但 Labeler 认领或被指派后进入答题页只看到一条题目,进度显示 `第 1 / 1 题`。
- 原因:数据集确实已经通过 `items.task_id` 绑定到任务,但答题页按 `assignments` 计算当前 labeler 的可作答队列。原后端在认领或指派时只给 labeler 创建 1 条 assignment,没有把数据集里的多条 item 转成多条 assignment。
- 处理:认领和指派逻辑改为批量创建 assignment;历史只生成 1 条 assignment 的任务会在“我的任务”列表和答题页读取时补齐。
- 后续建议:后续 Owner 端可以增加“每人领取批量大小 / 是否允许多标注员重复标注同一 item”的显式配置,避免把分发策略隐藏在后端默认规则里。

## 问题:接口文档梳理发现 Reviewer/Dashboard 后端未落地

- 原因:Reviewer 页面和 Dashboard 页面先按计划书完成了前端骨架和 API 调用层,后端仍停留在认证、任务、数据集、模板、认领和答题闭环阶段。
- 处理:已在 `接口文档.md` 中把这些接口标记为“前端已预留 / 后端待实现 / 未联调”,避免后续误判为已完成接口。
- 后续建议:优先实现 Reviewer 后端接口,打通 `annotations` 到人工审核的状态流转;随后实现 Dashboard 聚合统计接口。

## 问题:模板页显示“尚未绑定任务”但任务发布页已选择模板

- 现象:Owner 任务发布页中任务已经选择某个已发布模板,但模板列表卡片仍显示“尚未绑定任务”。
- 原因:任务发布页保存的是 `tasks.reward_rule.schemaVersionId`;模板列表原查询只看 `task_schema_versions.task_id`,没有识别任务元数据里的模板引用关系。
- 处理:后端 `/api/schemas` 查询已改为同时识别 `task_schema_versions.task_id` 和 `tasks.reward_rule.schemaVersionId`,并在响应中的 `taskId/taskTitle` 返回可展示的任务信息。
- 后续建议:如果同一个模板被多个任务复用,后续可把接口响应从单个 `taskId/taskTitle` 扩展为 `boundTasks[]`,让模板页展示完整使用清单。

## 问题:Formily 官方 antd 适配包与当前 antd6 不匹配

- 现象:动态表单计划要求接入 Formily,但 `@formily/antd-v5` 的 peer dependency 要求 `antd ^5.13.0`,当前前端项目使用 `antd 6.4.3`。
- 原因:Formily 官方 antd 包暂未直接对齐当前项目的 antd6 版本;强行安装会引入 peer dependency 风险,降级 antd 又会影响现有全站 UI。
- 处理:保留 antd6,只引入 `@formily/core`、`@formily/react`、`@formily/json-schema`,并自建 `formilyAntd6` 字段适配层。
- 后续建议:若 Formily 官方发布 antd6 适配包,可评估替换自建适配层,但需要先做全站表单回归。

## 问题:Designer 拖拽浮层不跟随鼠标

- 现象:Owner 模板 Designer 中拖动左侧物料或中间画布字段时,拖拽浮层相对鼠标出现明显偏移,看起来像“没有跟着鼠标走”。
- 原因:dnd-kit `DragOverlay` 使用 `position: fixed` 按视口定位,但当前应用外层 `.app-shell-enter` 动画结束后仍保留 `transform: translateY(0)`。CSS transform 会改变 fixed 子元素的定位参照,导致 overlay 坐标被外层容器偏移。
- 处理:将 `DragOverlay` 通过 React Portal 挂载到 `document.body`,让浮层脱离 transformed ancestor,恢复按视口坐标跟随鼠标。
- 后续建议:后续若新增其他基于 fixed 定位的拖拽浮层、截图框或跟随光标菜单,优先确认其是否需要 portal 到 `body`。

## 问题:Designer 拖拽时缺少明确放入位置提示

- 现象:拖动物料或字段到画布已有组件附近时,只能看到浮层,但不知道松手后会插到目标组件上方还是下方。
- 原因:原实现只依赖 dnd-kit `over.id` 判断当前悬停在哪个字段上,没有进一步判断拖拽中心点位于目标字段上半区还是下半区,也没有把该方向可视化。
- 处理:新增 `dropIndicator` 状态,在 `onDragOver` 中计算 `before/after`,字段卡片按该状态渲染红色插入线;最终 `onDragEnd` 也使用同一方向执行插入和排序。
- 后续建议:后续如果支持分组容器或多 Tab 内部嵌套拖拽,需要把落点模型从单层 `fieldId + before/after` 扩展为 `containerId + fieldId + position`。

## 问题:Designer 插入提示线总显示在组件下方

- 现象:拖动物料或字段时,即使鼠标位于目标组件上半区,红色插入线仍显示在该组件下方。
- 原因:字段卡片和外层画布都是 droppable,默认碰撞检测容易命中 `canvas-droppable`,从而走“追加到最后一个字段下方”的兜底分支。该轮修复时方向判断先改为鼠标 Y 坐标,以便快速验证上/下半区。
- 处理:自定义 Designer 碰撞检测,优先命中具体字段卡片;方向判断改为使用当前鼠标 Y 坐标与目标卡片中心线比较。
- 后续建议:如果后续出现横向布局、分栏或嵌套容器,需要把落点方向从单一 `before/after` 扩展为支持 `inside/left/right` 等更完整的位置模型。

## 问题:插入方向应按拖拽组件位置而不是鼠标点判断

- 现象:红线虽然能区分上/下,但当鼠标点位于拖拽组件边缘或拖拽手柄附近时,提示线可能和用户看到的拖拽组件覆盖位置不一致。
- 原因:上一轮方向判断基于鼠标 Y 坐标,而用户期望基于拖动组件本身相对目标组件的上半区/下半区。
- 处理:方向判断改为使用拖拽组件当前矩形中心线与目标组件中心线比较,使提示线跟随拖拽组件的视觉位置。
- 后续建议:如果后续字段卡片高度差异很大或引入缩放画布,需要补充真实浏览器拖拽回归,确认 dnd-kit `active.rect.current.translated` 与视觉浮层保持一致。

## 问题:任务使用中的模板不能物理删除

- 现象:模板已经被任务或 annotation 引用时,用户仍希望在模板管理页删除它。如果直接物理删除 `task_schema_versions` 记录,任务运行时会找不到 schema,历史 annotation 的模板外键和语义追溯也会被破坏。
- 原因:任务通过 `tasks.reward_rule.schemaVersionId` 引用模板版本,annotation 通过 `annotations.schema_version_id` 外键引用模板版本。模板数据既是管理对象,也是运行时和历史审计数据。
- 处理:删除改为软删除,新增 `task_schema_versions.deleted_at`。Owner 管理列表和新任务模板选择过滤软删除模板,但 Labeler 认领、作答、提交和历史查看仍允许读取已软删除模板。
- 后续建议:当前没有恢复入口。后续如果需要恢复误删模板,可增加 Owner 端“归档模板”视图,并把 `deleted_at` 置回 `NULL`。

## 问题:antd v6 CSS-in-JS 注入样式优先级很高,暗色模式覆盖大量使用 !important

- 现象:暗色模式下 `.field-option-tag.ant-tag`、Input、Select、Card 等 antd 组件的白底深字背景无法用普通 class 选择器覆盖,即使写了 `:root[data-color-mode='dark'] .xxx { background: ... }` 也被压住。
- 原因:antd v6 用 `@ant-design/cssinjs` 在运行时注入 `:where(.css-xxx).ant-btn:hover` 样式,这些样式写到 `<style>` 标签里,优先级与作用域比静态 CSS 文件略复杂,加上 inline style + token 算法干扰。
- 处理:
  1. 全局通配 `:root[data-color-mode='dark']` 使用 `!important` 强制覆盖底色和文字色。
  2. SVG `<text>` 用 `fill` 属性,需要专门给 `.donut-total / .donut-sub` 等 class 写 `fill: ... !important`。
  3. 渐变文字 `background-clip: text` 在暗色下退回 `--lh-primary-light` 实色字。
- 后续建议:antd v7 升级时检查 `theme.darkAlgorithm` 是否能直接覆盖更多场景,届时减少 `!important` 用量。如需要进一步降耦合,可改用 antd 的 `ConfigProvider.theme.components` token 体系,但当前散落在 200+ 处的覆盖一次性迁移成本太高,先维持现状。

## 问题:渐变模式下 antd Button 边缘暴露 1~2px 瑕疵

- 现象:渐变模式下主按钮和登录提交按钮左边缘有"小咬痕",尤其在 hover 时明显。
- 原因:antd Button 默认 `border: 1px solid transparent` + `::before/::after` 伪元素做点击波纹效果,渐变背景下 border-box 与 padding-box 边缘色阶差异在 1~2px 内被肉眼感知。
- 处理:`border: none` 改为 `border: 1px solid transparent`(让 border 宽度始终一致避免尺寸跳变),`background-clip: padding-box` 让背景延伸到边缘,显式 `display: none` 隐藏 `::before/::after` 伪元素。代价是失去波纹动画。
- 后续建议:如果产品要求保留点击波纹,可改用 `outline + outline-offset` 替代,但视觉一致性优先。

## 问题:hover "进入任务市场"时"查看草稿"按钮跟着动

- 现象:Labeler 工作概览 hero 横幅里两个按钮挨得近,hover 第一个时第二个按钮位置出现 1px 漂移。
- 原因:`.overview-hero-cta` 写了 `border: none`(border-width: 0),但 antd v6 hover 时 CSS-in-JS 注入 `border: 1px solid xxx`,从 0px → 1px 的 border 变化让按钮总宽度增加 2px,把右边按钮挤动。反向 hover 不动是因为另一个按钮始终有 1px border。
- 处理:`border: none` 改为 `border: 1px solid transparent`,hover 时也保持 `border: 1px solid transparent !important`,确保 border 宽度始终是 1px。
- 类似场景:其它紧挨的按钮组遇到 hover 联动时,统一用 transparent border 而不是 `none`。

## 问题:暗色模式 SVG 文字看不见

- 现象:数据看板 / Reviewer 报表的环形图中心数字"100"在暗色下完全看不见。
- 原因:SVG `<text>` 元素用 `fill` 属性控制颜色,而不是 CSS `color`。暗色模式的通配规则 `color: #e5e7eb` 对 SVG text 无效。
- 处理:专门为 `.donut-total / .donut-sub` 等 SVG class 在暗色下写 `fill: #f8fafc !important / fill: #94a3b8 !important`。
- 类似场景:今后任何用 SVG 渲染文字的图表,暗色适配都要单独写 `fill` 规则。

## 问题:状态机正确性不能只靠前端按钮控制

- 现象:计划书要求"状态机正确性",如果只在前端隐藏按钮或靠页面流程约束,用户仍可通过接口直接提交非法状态变化,也无法形成审计闭环。
- 原因:状态流转属于后端数据一致性规则,必须在事务内校验当前状态、目标状态、操作者角色和业务前置条件。
- 处理:
  1. 新增 `StateMachineService`,统一校验 task / assignment / annotation / ai_review_job / export_job 状态迁移。
  2. 扩展 `audit_logs`,把操作者角色、from/to 状态、原因和快照写入数据库。
  3. 任务、认领、提交、Reviewer 审核、AI Review、Export 都接入审计。
- 取舍:
  - 本轮不新增 review batch / dispute 表,批次和争议从现有 task / human_reviews 派生。
  - `REVISE` 不直接改写 Labeler 答案,只记录审核意见,避免答案归属和审计链路不清。
  - AI 真实模型调用暂不做,先落地 job/result/status/audit 闭环。
- 后续建议:
  - 如果需要多人审核分派、锁定批次、争议终审委员会等能力,再引入独立 batch / dispute 表。
  - Export 文件生成与下载可在导出状态机稳定后继续实现。

## 问题:模板发布出来和当前 Designer 配置不一致

- 现象:在 Designer 中配置好 ShowItem、单选、多行文本和联动规则后,点击"发布",重新打开模板或绑定任务时看到的内容像是旧配置,不是刚刚画布上的配置。
- 复现条件:
  1. 新建模板并保存成真实草稿版本。
  2. 继续修改字段属性,例如字段名、选项 label、联动规则。
  3. 不点"保存草稿",直接点"发布"。
- 原因:`handlePublish` 只在本地临时 `draft-*` 时调用 `saveDraft()`。已有真实 `versionId` 的草稿发布时直接调用 `POST /schemas/{id}/publish`,后端发布的是数据库里上一次保存的旧 schema。
- 处理:
  1. 发布前始终执行 `saveDraft()`,确保当前画布配置先落库。
  2. 保存成功后再调用 publish。
  3. 保存/发布后保留当前选中的字段,避免属性面板跳回第一个字段造成误判。
- 验证:用 `question_prompt / quality_result / reject_reason` 模板做接口级测试,发布后重新拉取字段、选项和 reaction 均保持一致。
- 后续建议:后续可以在 Designer 顶部增加"未保存改动"状态提示,但当前已经通过发布前强制保存解决数据不一致问题。

## 问题：任务发布只提示 Not Found 且模板发布后刷新看不到

### 现象

Owner 在任务发布 Drawer 点击“立即发布”时，页面顶部只显示 `Not Found`。同时用户反馈刚刚在 Designer 保存并发布的模板刷新后不见了。

### 排查

使用真实接口验证：

1. `demo / demo123`

   - 创建独立模板草稿成功。
   - 发布模板成功。
   - 刷新 `/api/schemas` 能查到该模板。
   - 使用该模板、数据集和指派策略创建任务成功。
2. `owner / owner123`

   - 使用已有已发布模板和自有数据集创建指派任务成功。

因此当前后端任务发布主链路是可用的；截图里的泛化 `Not Found` 需要结合后端业务错误码继续判断具体对象。

### 原因

1. 前端 `ApiError` 原来只把 HTTP `statusText` 作为错误文本，后端返回的 `{ code, message }` 被保存在 `payload` 中但没有展示。
2. 独立模板和任务的绑定关系保存在 `tasks.reward_rule.schemaVersionId`，部分后端查询仍只按旧关系 `task_schema_versions.task_id` 找模板，导致任务/答题回显路径对独立模板不够稳。
3. 如果用户在一个 Owner 账号下创建模板/数据集，又切到另一个 Owner 账号发布任务，后端按当前 Owner 重新校验时会返回 `SCHEMA_NOT_FOUND` 或 `DATASET_NOT_FOUND`。

### 处理

- 前端统一展示后端业务错误 `message/code`，不再只显示 `Not Found`。
- 后端任务查询和答题页 assignment 查询优先按 `tasks.reward_rule.schemaVersionId` 读取独立模板，兼容旧的 `task_id` 模板。
- 用 `demo` 和 `owner` 两个账号分别做接口级发布任务验证。

### 后续建议

如果页面再次报错，直接看新的提示文案即可判断下一步：

- `dataset not found`：当前登录 Owner 不是这个数据集的创建者，或页面选中了已失效数据集。
- `schema not found`：当前登录 Owner 不是这个模板的创建者，或模板已软删除。
- `published task requires a published schema`：模板不是已发布状态，可能刚被收回。

## 问题：任务物理删除会级联清空标注数据

### 现象

Owner 删除任务后，Labeler 端仍可能在旧列表或旧答题链接中看到任务；如果直接物理删除 `tasks`，数据库外键会级联删除 `assignments` 和 `annotations`，不符合“已标注数据作废但保留”的产品语义。

### 原因

1. 原 `DELETE /api/tasks/{taskId}` 执行 `DELETE FROM tasks`。
2. `assignments.task_id -> tasks.id ON DELETE CASCADE` 会删除认领记录。
3. `annotations.assignment_id -> assignments.id ON DELETE CASCADE` 会继续删除标注答案。
4. Labeler 查询没有任务删除态过滤，也没有 `voided` 终态。

### 处理

- 为 `tasks` 增加 `deleted_at`，任务删除改为软删除。
- 删除任务时把相关 `assignments.status` 和 `annotations.status` 标记为 `voided`，保留 `answer_json`。
- 清理相关 drafts，避免旧页面继续保存草稿。
- Labeler 市场、我的任务、答题页、草稿和提交接口全部识别删除/作废状态。
- Reviewer、AI Review、Export 查询排除 `voided` annotation。

### 取舍

- 本轮没有做任务回收站和恢复入口；软删除任务只从常规管理端和 Labeler 流程隐藏。
- 已导出的历史文件不回滚；删除后仅保证后续流程不再处理作废 annotation。
- 如果后续需要展示作废标注，需要基于 `audit_logs` 和 `annotations.status = 'voided'` 单独做归档视图。

## 问题：旧 `required` 联动只做条件必填，不能控制字段显示

- 现象：模板配置“质量判断 = 不通过 -> 问题说明必填”后，Labeler 答题页初始就显示“问题说明”，用户预期是点击“不通过”后才显示。
- 原因：旧 `required` 动作只修改 `required` 状态，不修改 `visible` 状态；Renderer 和后端校验没有“显示并必填”的复合动作。
- 处理：新增 `visibleRequired` 动作；Designer 新增“显示并必填”选项；Renderer、前端提交校验、后端 Schema 校验、后端答案校验全部支持该动作。
- 兼容取舍：旧模板中的 `required` 自动按“显示并必填”处理，避免已经发布的模板需要重建。代价是如果历史上存在“始终显示但条件必填”的 `required` 用法，本轮会改变其显示行为。
- 后续建议：如果产品后续需要两种语义并存，可新增 `conditionalRequired` 表示“始终显示但条件必填”，并逐步迁移旧模板。

## 问题：联动字段隐藏后，选择“不通过”仍不显示

- 现象：修复默认隐藏后，目标字段在“通过”和“不通过”下都不显示。

- 处理：前后端联动匹配都支持 option value 和 label 双向匹配；Renderer 按运行时规则状态重建 SchemaField。

## 问题：模板列表显示草稿但删除接口提示 only draft schema can be deleted

- 现象：Owner 模板卡片显示“草稿”，点击删除时后端返回 `only draft schema can be deleted`。
- 原因：列表响应使用 `normalizeStatus`，把非 `published` 展示为 `draft`；删除接口和 SQL 只认数据库状态精确等于小写 `draft`，历史状态值大小写、空格或旧状态会导致前后端语义不一致。
- 处理：后端删除和更新判断统一使用规范化状态；软删除 SQL 改为只拒绝 `published`。
- 后续建议：后续若新增更多模板状态，应把状态枚举收敛为明确白名单，避免“非 published 都是 draft”的兜底语义继续扩大。

## 问题：任务软删除后复用同一数据集导致 Labeler 认领返回 500

- 现象：Labeler 在任务市场点击“立即认领”时，`POST /api/tasks/{taskId}/claim` 返回 500。当前本地库中任务 `14` 可见且有剩余额度，但认领失败。
- 根因：`assignments` 原唯一键为 `(item_id, labeler_id)`，没有包含 `task_id`。任务 `11` 删除后留下 `voided` 历史 assignment，任务 `14` 复用同一数据集 item 时，同一个 Labeler 再次认领相同 item 会触发唯一键冲突。该冲突之前没有被转换成业务错误，最终变成 500。
- 处理：
  1. 新增 `V8__scope_assignment_unique_key_by_task.sql`，把唯一键升级为 `(task_id, item_id, labeler_id)`。
  2. 初始化脚本 `V1__init_labelhub_schema.sql` 同步调整唯一键。
  3. 可认领 item 查询只排除当前任务内已有有效 assignment，允许不同任务复用同一数据项。
  4. 插入 assignment 时捕获唯一键冲突并转换为 409 `NO_AVAILABLE_ITEM`，避免数据库异常冒泡。
- 取舍：本轮允许同一 Labeler 在不同任务中重新标注同一 dataset item，因为不同任务可能绑定不同模板、截止时间和审核流程；同一任务内仍保持唯一约束。
- 后续建议：数据集绑定任务当前是直接更新 items.task_id，历史 assignment 仍保留旧 task_id。后续如果要让同一数据集同时服务多个并行任务，更稳的模型是新增 task-item 映射表或任务数据快照表，但这会超出“不新增表”的当前约束。

- 现象：Owner 收回模板后把匹配值从“不通过”改成 `option_b`，保存并发布后数据库中 `quality_result` 的联动仍是 `value = "不通过"`、`action = "required"`；Labeler 选择“不通过”后“问题说明”不显示。
- 根因：
  1. 收回模板后 Designer 默认选中第一个字段，用户容易在 ShowItem 的联动页改值，而不是在“质量判断”字段的联动页改值。
  2. 旧联动规则使用 `required` 表示条件必填，但产品语义已经改为“显示并必填”。
  3. 匹配值存在 label/value 混用：单选真实提交值是 `option_b`，界面显示 label 是“不通过”。
  4. Renderer 之前主要依赖 Formily 的 `x-visible`，隐藏字段状态刷新不够直接。

- 取舍：旧 `required` 全部兼容为“显示并必填”。如果后续确实需要“字段始终显示、只是条件必填”，应新增独立动作，例如 `conditionalRequired`，避免和当前语义冲突。

## 问题：模板原地收回修改后，旧标注无法按旧模板回放

- 现象：模板使用同一个 `schemaVersionId` 原地收回、修改、重新发布后，历史 annotation 只有 `schema_version_id + answer_json`，无法知道提交时的字段结构。
- 根因：缺少 annotation 级别的 schema 快照。同一个 `task_schema_versions.id` 被原地修改后，旧答案引用的 schema 结构也随之变化。
- 处理：
  1. 新增 `annotations.schema_snapshot_json` 保存提交当时完整 schema。
  2. `latestAnnotation` 返回 `schemaSnapshot`，Labeler 查看已提交题目时按快照只读渲染。
  3. 重新修改时切回任务当前 schema，并通过 `schemaDigest` 防止旧页面误提交。
- 取舍：迁移前已经被覆盖的旧 schema 无法完整恢复，只能使用当前 schema 做 best-effort 回填；迁移后新提交的数据可严格回放。

## 问题：单题提交即进入审核不符合批次提交预期

### 现象

Labeler 在答题页每道题都看到“提交并继续”。点击后会立即创建 annotation、删除草稿，并进入 AI 预审/人工审核。用户期望是前几题只保存草稿，最后一题统一提交整批已领取题目。

### 原因

旧流程把每个 assignment 当成独立提交单元，前端“下一题”只是跳转，没有强制保存；后端也只有 `POST /assignments/{assignmentId}/submit` 单题提交接口。

1. 新增 `ai_review_rules`，并在 job 中保存 `rule_id` 与 `rule_snapshot_json`。
2. 扩展 result 字段，保存总分、风险标签、证据、模型名、延迟和原始响应。

- Agent 使用真实 Responses API，不做 mock；缺少 API Key 时 job 会失败并进入后端重试/人工兜底策略。

## 问题：Agent 失败日志只显示 500，无法定位失败来源

### 现象

Agent 能领取 AI review job，但日志只显示 `500 INTERNAL_ERROR`，审计日志中的 `reason` 也只有后端返回的错误文本。无法判断失败发生在 LLM Responses API 调用、后端 complete 回写，还是 fail 回写。

### 原因

`AiReviewWorker` 原先把 LLM 调用和后端 complete 回写放在同一个 `try/catch` 中，所有异常统一打印为 `AI review job ... failed`，再调用后端 fail。后端全局异常处理也没有记录未处理异常堆栈。

### 处理

1. Agent 拆分失败来源：
   - `LLM_CALL_FAILED`
   - `BACKEND_COMPLETE_FAILED`
   - `BACKEND_FAIL_WRITEBACK_FAILED`
2. 后端全局异常处理增加 error 级别堆栈日志。
3. 用临时 API Key 验证 `https://www.pqapi.store/v1` 的 `/models` 和 `/responses` 均可用，Agent 默认 base URL 改为该地址。

### 取舍

- 真实 API Key 仍只通过本机环境变量设置，不写入 README、配置文件或数据库。
- 后端响应继续隐藏堆栈，只在服务端日志保留详细异常。

## 问题：AI 审核 Job 长时间 running 无法人工处理

### 现象

AI review job 被 Agent 领取后停留在 `running` 很久，后台只能查看状态，不能取消或重新排队。用户需要在 Job 队列中对执行中的任务进行“取消并重新排队”，失败任务可以“重新执行”。

### 原因

原状态机只有 `pending -> running -> succeeded/failed` 和 `failed -> pending`，没有人工把 `running` 拉回 `pending` 的入口。同时缺少执行代次 token，如果直接把 running 改回 pending，旧 Agent 稍后 complete/fail 回写可能覆盖新一轮执行结果。

### 处理

1. `ai_review_jobs` 增加 `run_token` 和 `cancel_reason`。
2. Agent 领取 Job 时获得 `runToken`，complete/fail 回写必须携带 token。
3. 后端校验 token，不一致返回 `AI_REVIEW_RUN_STALE`，不修改 Job 或 annotation。
4. 新增 `POST /api/ai-review/jobs/{jobId}/cancel`，把 `running` Job 取消并直接回到 `pending`。
5. 前端 running Job 显示“取消并重新排队”，超过 10 分钟显示“疑似卡住”；failed Job 显示“重新执行”。

### 取舍

- 不新增 `cancelled` 状态，取消后直接回到 `pending`，符合当前产品选择。
- 为避免旧 Agent 回写污染新执行，必须引入 `runToken`，这是取消后直接回排队语义下的必要保护。

## 03 答题页:离散字段触发后没有自动跳下一题

### 现象

用户在答题页开启「填完自动下一题」开关后,点击单选题(如「通过/不通过」)选项,题目状态从未答 → 已答,但页面停留在当前题,没有跳到下一题。
出现场景:任意离散字段(单选/多选/tags)作为本题最后一个必填项时复现。

### 根因

两个 `useEffect` 在同一次 `setAnswer` 后并行重跑,执行时序与状态依赖打架:

1. `onChange` 触发后 React 调度同一批更新:`setAnswer(nextAnswer)` + `setDirty(true)`。
2. 两个 effect 都因 `answer / dirty` 变化重跑:
   - 草稿 effect 走「离散立即保存」路径:`setTimeout(0)` 立刻发请求,`saveCurrentDraft` 成功后调 `setDirty(false)`。
   - 自动跳题 effect 也排了一个 `setTimeout(200)` 准备跳题。
3. 草稿请求 200ms 内通常已经返回,`setDirty(false)` 触发自动跳题 effect 再跑一次:
   - 这次 effect 第一行守卫 `if (!dirty) return` 命中,
   - cleanup 函数清掉 200ms 跳题 timer,
   - 自动跳题被静默取消。

简单说:把"用户编辑过当前题"绑在 `dirty` 上,而 `dirty` 在草稿落库后会自然清零,导致跳题 timer 还没触发就被自身的清理函数清掉了。

### 修复

`frontend/src/pages/labeler/AnswerPage.tsx`:

1. 新增 `hasEditedRef = useRef<boolean>(false)`,只在 `LabelHubFormRenderer.onChange` 中设为 `true`,在切到新题(`applyItem`)时重置为 `false`。
2. 自动跳题 effect 的守卫从 `if (!dirty) return` 改为 `if (!hasEditedRef.current) return`。
3. 自动跳题 effect 的依赖数组中移除 `dirty`(改为依赖 `answer`,变更触发不变)。
4. 注释里说明清楚不能复用 `dirty` 的原因,避免后续维护时被"看起来没用的 ref"误删回老路径。

修复后:

- 离散字段:点完即触发,200ms 内自动跳下一题,中间的草稿落库不再影响跳题 timer。
- 连续字段:停止输入后 800ms 跳题,行为不变。
- 必填缺失/校验失败:`collectValidationErrors().length > 0` 仍能拦掉跳题。
- 回到上一题修改:`advancedAssignmentsRef` 已在跳前写入,守卫继续生效,不会重复跳。
- 切到新题:`applyItem` 中 `hasEditedRef.current = false`,新题重新计时。

### 验证

- `frontend/npm run build` 通过。
- 手动复现:开启开关 → 进入只有「通过/不通过」单选的题目 → 点「通过」→ 顶栏闪现「已自动保存,即将进入下一题」→ ~200ms 切到下一题。

### 后续建议

- effect 依赖里如果同时存在「触发条件」与「会被回调清零的状态」,优先把触发条件提到 ref,避免清零让 effect 自我取消。
- 类似模式后续如果出现在 Reviewer 工作台或 Owner 审核页(都有"操作完成 → 自动跳下一条"诉求),可以直接复用本期"hasEditedRef + force 保存"的写法。

## 2026-05-31 续期任务最后提交被历史不可编辑 assignment 卡住

### 现象

4. `claimed` 缺草稿或答案不完整仍返回 `BATCH_SUBMIT_INCOMPLETE`。
5. 本次没有新题需要提交时返回成功，`submittedCount=0`，前端提示“没有新的题目需要提交，已提交的题目正在审核中”。

### 约束

- 不重复提交已进入审核流或已通过的历史 annotation。
- 不改变截止结算、续期发布、返修窗口和单题提交状态机。


1. 前端 `streamAssistant()` 收到 SSE `event: done` 后只触发回调,但仍继续等待底层 HTTP 流自然结束。若后端连接收尾异常或连接迟迟不关闭,调用方 `await` 不返回,`pending` 一直为 true,输入框被禁用。

- 仍然保持直接 SSE 流式输出,不增加 JSON 回退机制。

## 2026-06-01 LLM 答题助手 SSE 异步分发被二次鉴权拒绝

### 现象

后端在 AI 助手流式输出后继续打印:

```text
AuthorizationDeniedException: Access Denied
Unable to handle the Spring Security Exception because the response is already committed.
Cannot render error page for request [null] as the response has already been committed.
```

堆栈包含 `AsyncContextImpl.doInternalDispatch`。

### 根因

`StreamingResponseBody` 会使用 Servlet 异步处理。初始请求已经通过 token 鉴权并开始写出 SSE 响应后,Tomcat/Spring 在流式响应收尾阶段会触发 `DispatcherType.ASYNC` 内部分发。

### 处理

1. `SecurityConfig` 显式放行 `DispatcherType.ASYNC`。
2. 同时放行 `DispatcherType.ERROR`,避免错误页内部分发在响应已提交后再次进入拒绝链路。
3. 初始 `/api/**` 的 `.authenticated()` 规则保持不变,真实 API 请求仍需 token。

### 约束

- 不放开普通 `/api/**` 访问权限。
- 不改变 LLM 助手接口协议。

## 手机局域网访问登录返回 403 Forbidden(CORS 白名单未含局域网 IP)

### 现象

PC 用 localhost:5173 能正常登录;手机在同一局域网用 http://192.168.8.171:5173 打开页面正常,但登录(含点演示账号)弹 `Forbidden`。错误是裸的 HTTP 403 statusText,不是后端业务的 `ROLE_MISMATCH`,说明请求未进登录业务逻辑就被拦。

### 根因

### 处理

把 `allowedOrigins`(精确匹配)改为 `allowedOriginPatterns`(通配),放行常见私有网段的任意端口:
`localhost / 127.0.0.1 / 192.168.* / 10.* / 172.16~31.*`。公网地址不在范围,符合最小必要暴露。

- 仅 dev/演示用途;生产应改为精确前端域名白名单。
- `backend/.\mvnw.cmd -q -DskipTests compile` 通过。

### 验证方式

## 2026-06-02 导出中心真实导出功能补齐相关问题

### 问题一:下载接口不能继续使用 `window.open`

真实下载接口需要 Owner Bearer Token。`window.open('/api/exports/{id}/download')` 不会自动携带前端保存的 Authorization header，容易导致下载请求被鉴权拦截。

### 处理

- 前端 `exportApi.downloadExport(exportId)` 改为 `fetch + Authorization + Blob`。
- 下载失败时解析后端 JSON 错误并抛出 `ApiError`，避免把错误响应当文件下载。

### 问题二:同步导出存在文件与事务短暂不一致风险

当前按计划采用“创建即执行”的同步导出。文件先写入本地目录，再写入 `files` 表和更新 `export_jobs`。如果文件写入后、事务提交前发生数据库异常，可能残留未关联的本地文件。

### 处理与约束

- 本轮不引入异步队列、不新增文件清理任务。
- 后续可增加定期清理策略:扫描 `labelhub.export.storage-dir` 下未被 `files.storage_key` 引用的导出文件。
- 当前接口层已校验下载路径必须位于配置的存储根目录下，避免目录穿越。

## 2026-06-07 LLM 触发组件未遵守模板联动且建议状态被重挂载清空

### 问题

- 模板中配置了 `choice_1 = B` 才显示并必填 `note_1`，但 LLM 生成结果可能同时建议 `choice_1 = A` 和 `note_1` 理由。

### 原因

- 后端 prompt 和结果规范化只知道目标字段列表，不知道 schema `reactions` 联动规则，因此无法判断某个目标字段在本次生成结果下是否应该显示。

### 处理

- 后端 prompt 加入联动规则摘要，并在模型结果后按“当前答案 + 本次生成值”重新计算联动可见性。
- 最终隐藏的目标字段建议自动过滤；最终可见字段缺失时返回业务错误。
- 前端把 LLM 建议状态提升到 `LabelHubFormRenderer`，按触发字段保存；普通表单值变化和联动重渲染不再清空建议。

## 2026-06-08 移动端顶部导航 fixed 受入场动画 transform 影响

### 问题

- `/owner/tasks` 手机端顶部导航虽然已经设置为 `position: fixed`，但实际滚动时仍没有稳定固定在视口顶部。

- 该问题和此前 LLM 助手悬浮按钮 fixed 定位受 transform 影响属于同类根因。

### 处理

- 在移动端断点内为 `.app-shell.is-mobile.app-shell-enter` 替换为只包含 `opacity` 的淡入动画。
- 显式设置移动端 `.app-shell.is-mobile.app-shell-enter` 的 `transform: none`。
- 保留桌面端原有带轻微位移的入场动画，降低视觉回归范围。

### 后续建议

- 后续新增移动端 fixed 浮层或悬浮按钮时，应检查其祖先链路是否包含 `transform`、`filter`、`perspective` 等会改变 fixed 定位参照的属性。

## 2026-06-08 Agent 登录后端 500：JSON_TABLE 参数写法不兼容

- AI Reviewer Prompt 卡片改为优先展示接口返回的 `promptSnapshot`。
- 后端新增保守的 mojibake 文本修复工具，并在 AI Review 响应出口与规则快照归一化中兜底。
- backend/agent 镜像和 docker compose 部署配置都显式固定 `Asia/Shanghai` 时区。

##### 后续建议

- 服务器更新后检查 backend/agent 容器内 `date` 和 JVM `user.timezone`。
- MySQL 执行 `SELECT @@global.time_zone, @@session.time_zone, NOW();`，确认会话时间符合北京时间。
- 本轮不迁移历史时间数据；如果历史记录确实已经按 UTC 写入，应另做字段级审计和迁移方案。
